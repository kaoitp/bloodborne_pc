## What the current failure establishes

The current same-map trial used two distinct authenticated accounts, copied EiEi characters in Cathedral Ward, a visibly matching nonempty password, selected-account mutual signaling and bidirectional self-hosted relay frames. Guest B explicitly called DeactivateConnection and sent ControlClose reason 1 after about six seconds; it never demonstrated JoinRoom/cooperator arrival. Later delivered-claim timeout cleanup is recovery after that first failure. A loaded distinct Kaori character with a crossed bell indicator did not produce an equivalent fresh claim trial. Copied-character collision remains an unproven hypothesis.

Offline native trace: host identity gate passed 73/73 scans with two matched/build observations; guest passed 0/89 and all observed candidates matched its own NP identity with candidate `user_id=0xffffffff`. Guest self-advertisement filtering may be normal. Do not bypass the identity guard, equate this 32-bit candidate field with a saved 64-bit server identity, or treat it as the deactivation cause. Raw captures and the derived identity analysis remain ignored; details are in the progress checkpoint.

The old server had returned success with an empty publish list; its later implementation returned durable positive IDs in `PublishCharacterIdList:[{PublishCharaId:...}]`. Its `identity_for` near 149-169 also stabilized per-account login identity after historical random IDs changed during play. The small hash-derived ID space there is not a recommendation for a new server design.

This is a reason to compare the current service's redacted identity/schema across login, sign, claim, native join and save/reload. It is not evidence that the deployed service has the same old bug: its exact source/version is unknown. Never clear saved sentinels, assign new account IDs, copy whole saves or redeploy as a diagnostic shortcut. Candidate `user_id` is read as u32 at candidate +0x14 (PIN core 2281-2315); no equivalence to these saved u64 fields has been established.

Reuse its questions, not its whole managed journal/admission machinery.

## Adaptation for the next native experiment

Trace the first missing transition in order: authenticated identity -> fresh sign/search/selected claim -> response consumed by the guest -> native game peer/session handshake and JoinRoom -> joined state -> native target-map arrival -> placement beside the selected host -> own-world return. Mutual signaling proves only one part of this chain.

1. **Control eligibility and stale state.** Use fresh processes and copied, bell-eligible characters, confirm password and exact supported region, reset host search/sign state, and record pre-join snapshots. Start same-map; change one variable per retry. Compare distinct characters with the copied-character case only after both produce equivalent claims. Stop the first trial at guest's first deactivation and preserve the preceding timeline.
2. **Use existing HTTP capture first.** CURRENT HTTP 725-789 already supports `SHADPS4_CAPTURE_BLOODBORNE_SUMMON=1`. In the ignored launch helper, set it after inherited environment cleanup for each isolated test process. Verify effective environment and resolve `CapturesDir/bloodborne-summon` under that copied profile; do not assume a directory without observing it. It writes `-request.bin`, `-response.bin` and metadata with method/URL/status/errors/placement headers. Capture does not send extra HTTP requests. This document does not enable it or launch a client.
3. **Prove consumption, not just capture.** CURRENT HTTP captures at 1810 before shutdown/deleted/aborted handling at 1813-1823; a captured response may subsequently be dropped. Correlate each process's request ID, request/claim generation, completion, actual read bytes/cursor, abort/delete and DLL ReadData observation. Existing DLL claim logging near 573-627 merely recognizes a UserId in the response; it does not validate the whole expected schema or selected host. First inspect existing logs; add only missing bounded instrumentation after identifying the unobserved boundary.
4. **Compare identity domains explicitly.** Derive a redacted field/type/schema table and stable per-run pseudonyms for host/guest numeric IDs, session, character and NP/Matching2 identities. Compare the actual selected claim to the pinned consumer and intended host. Raw request/response can contain matching words, sessions and account data: keep them ignored, never paste/stage them. Do not assume two different identity domains should be numerically equal.
5. **If the guest consumed a valid claim, follow the native game handshake.** Correlate game socket/callback activity, JoinRoom invocation/result and the first caller/error leading to DeactivateConnection. Signaling/relay frames alone do not validate native game protocol. If consumption fails first, fix that proven boundary before changing teleport, discovery timing or saved identities.
6. **Qualify placement only after native join works.** Reproduce supported cross-map and Hunter's Dream, including a host map still locked in the guest's own world. Observe native map consumption, resolve the selected host actor, place once beside it and verify no extra reload/warp loop. Include another available partner to catch wrong-host fallback. Failed/stale/wrong candidates must leave guest-world state unchanged. Then separately qualify G2 and normal/interrupted G3 with before/after save evidence.

Discriminators: invalid/wrong-host claim or a dropped/unread response supports an HTTP/identity boundary fix; a valid consumed claim followed by a failing game handshake supports a native session fix; equivalent fresh claims that succeed only with distinct characters support a character-state investigation. A six-second failure with a retained fresh placement weakens the ACK-expiry hypothesis. No outcome is assumed in advance.
