## Composition and callers (summary; R02 owns the evidence)

- **Transport patch versus gameplay.** The 15-file patch changes transport only:
  - the UDP relay fallback (`p2p_sockets.cpp`)
  - the signaling rejoin fix
  - `sceNpLookupNpId`
  - Matching2 peer endpoints
  - registration in `bbnet_glue.cpp`

  The BBport shim deliberately leaves `OnBbscHostFollowPacket` and `OnBbscWorldFlagsPacket` empty. Its comment: "BBSC frames … are handled by the BBSC mod DLL through the relay and its own P2P channel; the emulator side only ignores them" ([K gpu/shim/core/bloodborne_re.h L14-18](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/gpu/shim/core/bloodborne_re.h#L14-L18)). Inside the DLL, the same names are real handlers fed by the relay or channel dispatcher ([B emulator/mod/bbsc_relay.cpp L285-298, L345-348](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_relay.cpp#L285-L298)).
- **Gameplay owner: `bbsc.dll`.**
  - It is built from `bbsc_mod.cpp`, `bbsc_hooks.cpp`, `bbsc_relay.cpp`, `bbsc_channel.cpp`, `bbsc_http.cpp`, `bbsc_discord.cpp` and `bbsc_memscan.cpp`, plus all of `bloodborne_re.cpp` compiled with `/DBBSC_MOD` ([B emulator/mod/build-mod.cmd L1-17](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/build-mod.cmd#L1-L17)).
  - It uses MSVC clang-cl, which is absent in R02, so R02 uses the official DLL (SHA256 `1df7d39e…0fdf`).
  - Its byte patches come from `bbsc_patch_tables.h`, and its message tables are generated.
  - Kit data is read from the user's game tables (R02).
- **Injector and environment path.**
  - BBport `run.py` runs `BB_PROBE` as the game executable ([K run.py L270](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/run.py#L270)).
  - `bbsc-launch.exe` starts `BBSC_EMULATOR` (`bb-probe.exe`) suspended, calls a remote `LoadLibraryW` on the DLL, then resumes it. For bb-probe it keeps the working folder and passes no `--game` ([B emulator/mod/bbsc_launch.cpp L261-279, L351-380](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_launch.cpp#L261-L279)).
  - The DLL waits for the image, checks every patch site, writes them, installs the hooks, starts the relay and P2P channel, and wraps the HTTP import slots ([B emulator/mod/bbsc_mod.cpp L380-455](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_mod.cpp#L380-L455)). R02 observed 52 patch writes and 159/159 hooks (Codex).
  - The release's `tools/play-bbport.ps1` sets this environment. It ships only in the zip and is **not tracked at B**.
- **Manifest and defaults.**
  - `mod.json` ([B](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/mod.json)) lists the user switches.
  - The defaults that actually apply are `DefaultOnSwitches` ([B emulator/src/core/bbsc_persistence.h L16-51](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/src/core/bbsc_persistence.h#L16-L51)), which include `SHARED_PROGRESS`, `CONNECT_FIRST`, `WORLD_SYNC`, `WORLD_SYNC_ALL` and `BELLS_ANYWHERE`.
  - R02 checked the notices.

It is marked given only after the award is confirmed, and repeated departures or reloads cannot give it twice. A valid admission whose owner is merely inactive is deferred, not discarded. **Remaining design constraints:** the B-24 key can name the wrong slot, so owner matching inherits that gap; the queue is process memory, so an unsettled obligation does not survive a crash or exit (not a request for persistence); whether the area test passes during a join load into the boss's area, and whether the native award succeeds, are runtime questions |

### Smallest existing P01 seam (candidate for Codex; not implemented, not implementation-ready)

- **Where.** Filter at collection, not at merge: in `OnBbscProgressPacket` (flags) and in the kind-1 loop of `TickBbscSharedProgress` (groups). Then the collection, the pending file, crash recovery and the merge all carry only what the filter admitted, and `MergeBbscSharedProgress` stays unchanged.
- **What.** A first-seen baseline is a candidate against the bulk import of older history (G2-01) only:
  - Keep a baseline per flag and per group key, and admit only 0→1 transitions after it, for entries in A-23.
  - **It does not meet outcome 9 by itself.** Constraints C1-C4 (IDENTITY-PROTOCOL § CL02-B) are open: a delayed pre-playable observation can become the baseline (C1); the first eligible event can be swallowed (C2); reordered data defeats admit-once on the first admission (C3); the reset point needs a genuine new party or host epoch, not every state-6 entry (C4). The existing signals cannot close them (B-26..B-28).
  - Leave A-24, A-25 and A-26 out until they are classified. For the kind-1 groups this means either collecting nothing, or only bits Codex verifies for the 19 events. The source does not supply bit positions.
- **Rewards: two separate concerns.**
  - (i) **Admission and queue ownership** (A-27, A-32). Keep two times apart. **Eligibility when earned:** playable readiness opens the party's eligibility window once; the window stays open through that party's death and loading and closes only at genuine departure or a new epoch. Admit events earned in the boss's area while it is open, and record the owner (B-24 key) and the party epoch with the entry; reject an event earned while it is not open. **Delivery:** gated separately (owner loaded, alive, not loading, item manager readable). An admitted entry is held through same-party death and loading; at departure it is confirmed before the departure completes, or settled exactly once afterward for its original owner and epoch. While another character or a later party is active it is deferred, never awarded to them and never discarded for that reason. Discard only invalid admissions (unearned, stale, missing or invalid owner record), not a valid obligation to an inactive owner and not every outstanding earned one. Mark given only after a confirmed award. Keeping the existing state-6 enqueue, the ungated tick and the award-time area test does not satisfy G2-03 or G2-19(c1).
  - (ii) **Cross-run duplicates** (A-29). The get-flag check for the 5 rows with a get flag. It does not address (i).
- **What source cannot establish:**
  - which A-23 flag belongs to which of the 19 events;
  - whether any kind-1 bit is an NPC phase;
  - names or progression roles of the unnamed goods;
  - whether the 7 Codex entries are A-23, A-24 or A-25 members. The log line counts all 57 listed flags as "boss flags".
- **No new storage, auth or protocol framework.** The baseline lives in the collector's memory. The pending-file header already has a magic number that can mark filtered data (IDENTITY-PROTOCOL B-23). Where the existing signals are insufficient (event time, order, epoch, playable gate on rewards), this section says so instead of proposing a new framework.

### Decision

**NOT IMPLEMENTATION-READY.** No existing public-source signal binds an earned event to an eligible member and party epoch end to end:

1. **The only guest-side signal with an event ID (B-35) has no earn time.** It fires when the guest's copy of the event evaluates its wait. Pre-party kills are copied into the guest's world before play, so the signal may fire for them (M1).
2. **The only guest-side kill-time signal (B-34) has no event ID**, and whether it runs for a dead or loading guest is unknown (M2). Area pairing is ambiguous for 11 of the 19 rows.
3. **No signal carries an attempt or epoch.** The host relay id distinguishes host processes only (B-31). The first-placement flag (B-32) is per state-6 stretch and is not stored with any entry. A host id plus a placement marker does **not** establish a new-party boundary: a same-host rejoin within 5 s, or a host character change in the same process, keeps the same id. C4 is an independent blocker for every candidate.
5. **No source guarantee against stale world-state input.** Local callbacks (B-34, B-35) can be driven by older applied host state (B-26, B-35). Delayed or reordered input is unresolved, not excluded (C3).
4. **Host-side flags (B-36) carry no event or time**, and the flag ↔ event map is missing (M4).

**M1 and M3 are necessary, not sufficient (CL03-REV01).** Even if M1 shows the wait fires only at a kill and M3 shows state 6 holds through death and follow loads, K1 remains blocked on two further points:

- **C4.** A new party must be separable from a continuing one. G2-22 must show a distinguishable boundary for a same-host rejoin (under and over 5 s), for a host character change in the same process, and for a new host. If the existing signals cannot separate them, C4 stays open and no candidate is implementation-ready.
- **C3.** A wait must not be triggered by delayed or older applied host state. G2-17 must be paired with the reward line, or source must prove it.

Only after those would storing the B-31 host and a window marker on the entry, and relaxing P's enqueue area test for follow loads, be a justified small delta. K2 additionally needs M2.
