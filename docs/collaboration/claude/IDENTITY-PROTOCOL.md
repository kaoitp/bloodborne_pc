### Same-host versus split-host settings

The release's own scripts assume **one address** for everything: `play-bbport.ps1` writes 20443 and 31315 from the single account server, and the UDP relay defaults to the shadNet address. These scripts exist only in the release zip and are not tracked at B. In a split layout (shadNet on host S, game server on host G) the following must hold:

## 2. TCP :20444 relay versus the fallbacks: what cross-map join needs

**Finding B-F1 (conditional source hypothesis; revised by CL01-REV01): without the TCP relay, a cross-map join may stall because the aimed placement can miss the guest.** The source does not decide it. The ordering questions below do. Source facts:

1. The guest DLL learns the host's placement **only** from relay frame `0x31` aimed at its `UserId` ([B bbsc_http.cpp `OnAimedHostPlacement` L726-746](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_http.cpp#L726-L746)). Older broadcast placements are ignored (L708-725).
2. The broker's reply header does carry the placement. The game does not import `sceHttpGetAllResponseHeaders` (B bbsc_http.cpp L21-24). The emulator does read the header, but stores it in **its own** `bbnet_glue` copy ([K http.cpp L1799-1808](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/gpu/shadps4/core/libraries/network/http.cpp#L1799-L1808); [K bbnet_glue.cpp L318-337](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/gpu/bbnet/bbnet_glue.cpp#L318-L337)). That copy is separate from the DLL's own `GetSeamlessHostPlacementHeader` in its compiled `bloodborne_re.cpp`.
3. With no relay socket, `SendFrame` hands the frame to `P2PChannelSend`, which sends only to live channel peers ([B bbsc_relay.cpp L182-197](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_relay.cpp#L182-L197)). The host sends the aimed frame **once per claim request**, from the claim wrapper ([B bbsc_http.cpp L507-524](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_http.cpp#L507-L524); `RelaySendAimedPlacement`, [B bbsc_relay.cpp L491-496](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_relay.cpp#L491-L496); no resend there). Channel peers come from the game's P2P datagrams **or** from a signaling connection reported ACTIVE ([B bbsc_channel.cpp L161-170](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_channel.cpp#L161-L170)). So the native pre-join signaling phase can give the host the guest as a peer. The earlier claim that no peer can exist before the join does not follow from the send path.
4. Without the placement, the guest's `/create` keeps its own `AreaId`. The broker then answers a claimed cross-map sign with `{Claimed, no claim body, placement}` until the `AreaId` matches ([N `Advertise` L392-398](https://github.com/Wozzardman/shadnet-p2p/blob/5a849a192fd4450593c57b10697316ac324c856e/src/bloodborne_summon_broker.cpp#L392-L398)).
5. A same-map join does not need the placement: the `AreaId` already matches, so the claim is delivered.

**Not established from source (decides B-F1):**

- (a) whether the host's signaling connection to that guest is ACTIVE, and its status polled within the last 20 s, when the claim request is sent, or only afterwards;
- (b) whether a later claim of the same sign (a host retry) sends the aimed frame again after the connection became ACTIVE;
- (c) whether the default-on `CONNECT_FIRST` path changes what the guest needs before the join.

Until a native trace settles (a)-(c), channel-only cross-map joining is neither shown to fail nor shown to work. **No unconditional :20444 prerequisite is claimed.** If SVC-03(a) reproduces a stall, the smallest fix is still configuration (keep the existing relay reachable); no code change is proposed from source alone.

**Current evidence, kept separate (Codex):** R02 on 2026-10-23 saw :20444 unreachable. On 2026-10-24 the R03/R04 records show the pinned DLL connected to :20444, and Cathedral Ward → Dream joins succeeded ([R04-JOIN-RELOAD.md at bd24679](https://github.com/kaoitp/bloodborne_pc/blob/bd24679c7655a97bd4d9fba2b11ee079e6033751/docs/handoff/R04-JOIN-RELOAD.md); [WINDOWS-PROGRESS.md at bd24679](https://github.com/kaoitp/bloodborne_pc/blob/bd24679c7655a97bd4d9fba2b11ee079e6033751/docs/WINDOWS-PROGRESS.md)). This establishes relay-backed success, not relay necessity.

**After a join**, follow, world flags and progress (`0x20`, `0x22`, `0x26`) can travel over the P2P channel, because by then the game's P2P traffic gives both sides their peers. In that case the guest accepts host-only packets with `session == sender == locked host` ([B bbsc_relay.cpp L281-335](https://github.com/CLSAMG22/BBSC/blob/4f11faf88b6ba658ebde6fe5fbefdadedba4fa41/emulator/mod/bbsc_relay.cpp#L281-L335)). The locked host is set only by the aimed placement (`NoteBbscHostRangOurSign`, B bbsc_http.cpp L736), so on a channel-only setup the guest may never lock a host for **any** join. That needs checking (Q2).

**UDP 3478 (B-07)** carries the game's own frames, not BBSC's. The client's `P2P relay fallback: server …` line ([K p2p_sockets.cpp L606-611](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/gpu/shadps4/core/libraries/network/p2p_sockets.cpp#L606-L611)) proves the selected configuration, and the server's `shadPS4 relay: <npid> registered from …` proves registration. **Both are preflight results only**: they can exist while peer frames never reach the other client. **Route proven** requires, during an actual peer exchange, correlated bidirectional counters on both clients: `P2P relay fallback: <n> frame(s) sent / <m> received through the relay so far; peers: <id> relay`, with both counts rising and each client naming the other ([K p2p_sockets.cpp L754-772](https://github.com/kaoitp/bloodborne_pc/blob/04c6e7b4b9a042c872e6ed815dacce6c7a7a0d8e/gpu/shadps4/core/libraries/network/p2p_sockets.cpp#L754-L772); the receive counter grows only for relayed frames, L948), or equivalent captured forwarded frames on the server. A TCP port check proves neither protocol nor authentication.

### Unresolved correctness constraints for any first-seen baseline

A first-seen baseline can stop the bulk import of the host's older history (G2-01). It is **not** an implementation-ready answer to outcome 9. Each constraint below is open. The existing signals are not enough to close it.

1. **C1. Delayed pre-playable data becomes the baseline (false positive).** "First observation received at or after the playable start" is not a safe rule. H kills boss K before G is playable. A flags packet sent before the kill, or a snapshot N of K's block produced before it, arrives after the playable start and becomes the baseline without K. The next packet or snapshot holds K, so K turns 0→1 after the baseline and is admitted, although it was earned before admission. Comparing `complete_ms` with the playable start does not help, because it is local assembly time (B-27). Insufficient signals: no host event or send time, no flags sequence, no snapshot order (B-26, B-27). Cases G2-03, G2-15.
2. **C2. The first eligible event is swallowed (false negative).** G is playable and they kill K together before the first post-playable observation of K's flag or block. The kill is folded into the baseline and never admitted. Flags: the window is up to one 5 s period plus delivery. Groups: up to a whole block cycle, longer while the host loads (B-17). Accepting and documenting this loss does **not** meet outcome 9. The reward event (A-27) is the only existing participation signal, but it is not playable-gated (A-27) and does not name a flag (A-23), so it cannot close C2 as written. Case G2-16.
3. **C3. Reorder and admit-once.** Flags packets have no sequence; snapshots have no ordering check (B-26). An older full set or snapshot after a newer one shows a flag or bit 1→0→1. "Admit once, never remove" prevents a **second** admission. It does not prevent the **first wrong** one: if the baseline came from the older data (C1), the first 0→1 is already wrong. The freshness check of B-26 is a candidate only. Case G2-17.
4. **C4. Baseline reset needs a genuinely new party or host epoch.** Resetting on every state-6 entry is not justified: Q8 leaves open whether a same-party death, a kept death reload or a follow load leaves state 6. A reset there would fold an in-session kill into a new baseline and break outcome 9's "through death and loading". The product requires eligibility to be **kept** through those transitions. A reset is needed only for a new host or party, so that a second host's older history is not compared against the first host's baseline. The existing signal for that is a lock change (B-28), and whether it marks exactly the party boundary is unproved. Entries admitted in an earlier epoch of the same run stay admitted. Cases G2-11, G2-18.

The source guarantees only the shapes: a full set per flags packet and a whole block per completed snapshot. Order, event time and epoch boundaries are not guaranteed by source (B-26..B-28). All timing above is a runtime question, and any freshness or epoch rule is a candidate until Codex's reproduction and native gates pass.
